## 一、執行上的問題

找到三個 bug，已修正於 `frontend/src/ProductDB.js`：

### Bug 1（有實際影響）：切換分類不清狀態

**位置**：`ProductDB.js` 探索領域 onClick  
**問題**：點「化妝品」時只清了 `item`/`skinType`，沒清 `effect`/`finish`/`coverage`。若用戶先在保養品選了「保濕」，再換到化妝品，後端還是收到 `effect=保濕` 影響查詢。  
**修正**：onClick 改為全部狀態一併清除。

### Bug 2（死碼）：`MAKEUP_EFFECTS` 常數

**問題**：化妝品已改走妝感/遮蓋度路線，此陣列永遠不會被用到，但程式碼仍引用（ESLint 報錯）。  
**修正**：移除常數及相關引用。

### Bug 3（廢物 state）：`anchorRect`

**問題**：有 `setAnchorRect(...)` 被呼叫，但值從未被讀取，`ProductPopover` 也沒接收它。  
**修正**：移除 state 宣告及 onClick 內的呼叫。

## 三、前後端相容問題

只有一個隱患需要注意：

### DB 欄位遷移（重要）

`products` 表新增的 `finish`/`coverage` 兩欄是在 Supabase SQL Editor 手動執行的，**這不在 git 裡**。隊友 pull 下來後端程式碼後，資料庫不會自動跟著更新。

**解法**：把以下 SQL 告知隊友，讓他們在自己的 Supabase 專案執行一次：

```sql
ALTER TABLE products ADD COLUMN IF NOT EXISTS finish TEXT;
ALTER TABLE products ADD COLUMN IF NOT EXISTS coverage TEXT;
```

其他部分完全相容：
- API 回傳格式 `{ data, total, page, limit }`，前端正確解析
- 前後端膚質名稱完全對齊（`乾性肌`、`混合性肌` 等）

## 五、推薦清單依據

### 產品資料的真實性

**產品名稱和品牌是真實的**（Maybelline、L'Oréal、CEZANNE 等均為市售真實商品）。

**評分數據是人工整理的，非爬蟲或廠商官方提供：**

- `ingredients` 表的每個成分有手動填寫的加權值
  - 例：玻尿酸對乾性肌 `skin_dry = 2`、酒精對乾性肌 `skin_dry = -2`
- 保養品推薦分數 = 產品所含成分的加權值加總
  - 選「乾性肌」→ 含玻尿酸的產品分數高、含酒精的產品分數低
- 化妝品的 `finish`/`coverage` 是依照產品知識手動填入 DB

> 定性：這是「專家整理的人工標記資料」，不算假資料，但也不是第三方驗證過的客觀數據。

---

### 保養品 vs 化妝品：兩套推薦機制詳解

保養品與化妝品走完全不同的路線，在後端 `routes/products.js` 以 `isMakeupItem` 旗標切分。

#### 保養品 — 成分評分機制

**流程：**

```
使用者選膚質/功效
  → 對應 ingredients 表欄位（skinCol / effectCol）
  → 撈出每個產品的所有成分及其對應欄位數值
  → 逐成分累加分數（基礎分 3，每個有效成分 +/- 加減）
  → 過濾掉分數 < 3（負成分多的產品被排除）
  → 依分數高→低排序
  → 顯示推薦分數進度條
```

**膚質對應欄位：**

| 使用者選擇 | ingredients 欄位 |
|-----------|----------------|
| 油性肌 | `skin_oily` |
| 乾性肌 | `skin_dry` |
| 敏感性肌 | `skin_sensitive` |
| 中性肌 | `skin_normal` |
| 混合性肌 | `skin_combo` |

**功效對應欄位：**

| 使用者選擇 | ingredients 欄位 |
|-----------|----------------|
| 保濕 | `effect_hydration` |
| 控油 | `effect_oil_control` |
| 舒緩修復 | `effect_repair` |
| 抗痘 | `effect_anti_acne` |
| 去角質 | `effect_exfoliate` |

**分數計算範例（選「乾性肌 + 保濕」）：**

```
產品 A 含有：玻尿酸（skin_dry=2, effect_hydration=3）、Niacinamide（skin_dry=1, effect_hydration=1）
→ 分數 = 3（基礎）+ 2 + 3 + 1 + 1 = 10  → 強烈推薦

產品 B 含有：酒精（skin_dry=-2）、香料（skin_dry=-1）
→ 分數 = 3 - 2 - 1 = 0  → 被過濾掉（< 3）
```

---

#### 化妝品（粉底液、遮瑕）— 屬性直接過濾機制

**流程：**

```
使用者選妝感/遮蓋度
  → 直接對 products 表 WHERE finish = '...' AND coverage = '...'
  → 所有符合的產品平等顯示（score 固定為 3，不計算）
  → 不顯示分數進度條
```

化妝品完全跳過成分評分邏輯，原始碼如下：

```js
// routes/products.js
if (isMakeupItem) return { ...product, score: 3 };  // 直接跳過，不計算
```

**對應篩選欄位：**

| 使用者選擇 | products 表欄位 |
|-----------|---------------|
| 霧面 / 自然 / 光澤 | `finish` |
| 輕薄 / 中等 / 全遮蓋 | `coverage` |

---

#### 比較總表

| | 保養品 | 化妝品 |
|---|---|---|
| **推薦依據** | 成分對膚質/功效的加權分數 | 產品本身的外觀屬性 |
| **膚質篩選** | 有（透過成分分析） | 無（UI 層已隱藏） |
| **成分計算** | 所有成分逐一累加 | 完全跳過 |
| **排序方式** | 分數高→低 | DB 自然順序 |
| **分數進度條** | 顯示 | 不顯示 |
| **過濾邏輯** | 分數 ≥ 3 才保留 | 無過濾，全數顯示 |

#### 為何這樣設計？

買粉底液的人主要考量「要霧面還是水光」、「遮蓋力夠不夠」，這些是**產品本身的規格屬性**，跟膚質成分無直接關係；買乳液的人才需要知道「這瓶對油性肌的成分組合有多友善」。兩者關注維度不同，因此分開處理是合理的設計。

## 附錄：化妝品成分評分的可行性分析

### 問題背景

是否能用和保養品相同的「成分加權評分」機制，根據成分自動推算化妝品妝感（霧面/水光/自然）？

### 成分與妝感對應關係

| 妝感類型 | 代表性成分 |
|----------|-----------|
| 霧面/控油 | Silica、Talc、Kaolin、Nylon-12、Perlite、Trimethylsiloxysilicate、Alcohol Denat.、Isododecane |
| 水光/光澤 | Glycerin、Squalane、Sodium Hyaluronate、Mica、Synthetic Fluorphlogopite、Bismuth Oxychloride |
| 自然/半霧面 | Dimethicone、Glycerin、Silica、Titanium Dioxide、Iron Oxides（同時含有上述兩類） |

### 技術可行性

完全可行。需要執行以下步驟：

1. 在 `ingredients` 表新增 `finish_matte INT4`、`finish_dewy INT4` 欄位
2. 新增約 10–15 筆妝感型成分資料並填入對應權重
3. 為 40 個化妝品建立 `product_ingredients` 關聯
4. 後端改寫：化妝品查詢時計算 finish 分數而非直接比對欄位

### 建議結論：現階段不值得做

| 考量 | 說明 |
|------|------|
| 現況已夠用 | `finish`/`coverage` 手動欄位已填好，精準度比成分推算高 |
| 成分推算是預測 | 手動填寫是確認，後者更可靠 |
| 維護成本高 | 需要長期維護成分-妝感對應資料 |
| 適用時機 | 產品量成長到幾百筆、手動填 finish/coverage 太費力時才值得導入 |
